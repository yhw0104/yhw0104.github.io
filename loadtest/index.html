STEP 02

원인DB CPU 병목

앱 서버 CPU 사용률은 평균 1.9% 수준에 머문 반면, DB CPU가 2개 코어를 완전히 점유(197%)하고 있었다.
커넥션 풀 부족 현상은 DB CPU 포화 이후 연쇄적으로 발생한 결과일 뿐, 근본 원인은 DB의 CPU 과점유였다.

② 검색 한 번에 DB가 722ms를 쓴다

실제 호출 쿼리를 수집한 결과, 1회 검색마다 2개의 쿼리가 연속 실행되고 있었다. 

목록 조회   424ms
개수 세기   298ms
─────────────────
           722ms   ← 응답 730ms와 일치

원인 1목록 조회 지연 — 전체 데이터 정렬(Name-order Sorting)

상위 20건만 조회함에도 조건에 맞는 행 전체를 추출해 정렬을 수행했다. 예를 들어 '김밥' 검색 시 매칭되는 10,135건을 정렬하기 위해 전체 65만 행 테이블 스캔이 발생했다. 

정렬 미적용      →   0.7ms
이름순 정렬 적용 → 215.7ms

원인 2Count 쿼리 지연 — 전체 행 스캔(COUNT(*))

무한 스크롤 구현 과정에서 전체 데이터 개수 산출을 위한 COUNT(*) 쿼리를 추가적으로 실행했다.

화면에는 20건만 노출하지만, 전체 개수를 파악하기 위해 조건에 맞는 65만 개 행 전체를 세면서 298ms의 지연이 추가 발생했다.

③ 2글자 검색만 유독 느린 이유 — 실행계획이 갈린다

검색어 길이별 응답 시간을 비교한 결과, 2글자 구간만 결과 건수와 무관하게 113~124ms로 일정한 지연이 발생했다(5,731건이든 20,964건이든 동일). 소요 시간이 결과량에 비례하지 않는다는 것은 매번 테이블 전체를 스캔하고 있음을 의미했다. 

'김밥' → 예상  355건, 실제 3,378건  ( 10배 오차)
'커피' → 예상   27건, 실제 2,963건  (110배 오차)

원인실행계획 오선택 — 예상 건수(Cardinality) 오추정

DB 옵티마이저는 예상 결과 건수(Cardinality)를 기반으로 인덱스 스캔과 풀 테이블 스캔 중 효율적인 방식을 판단했다. 그러나 와일드카드가 앞뒤로 붙은 검색(%김밥%)은 데이터 분포 예측이 어렵다. DB는 실제 결과 건수를 최대 110배까지 오추정하여, 인덱스를 타는 대신 풀 테이블 스캔(Full Table Scan)이 더 유리하다고 오판했다.

반면 3글자 이상부터는 파싱된 검색어 조합이 구체화되어 카디널리티 추정 오차가 줄어들었고, 정상적으로 인덱스를 타는 실행 계획을 선택했다.

④ 위치 기반 검색은 꺼낸 데이터의 99%를 버린다

반경별로 DB가 실제 스캔하는 행 수와 소요 시간을 측정했다. 쿼리 실행 비용이 반경의 면적(제곱)에 비례하여 증가했다.

원인이름 조건의 사후 필터링(Post-filtering)

좌표 인덱스에는 식당 이름 조건이 포함되어 있지 않았다.

이로 인해 DB는 지정한 반경 영역(Bounding Box) 내부의 모든 데이터를 먼저 전부 읽어들인 뒤, 이름 조건으로 걸러내는 사후 필터링 방식을 수행했다.

기존 10km 반경 조건에서는 77,067개 행을 스캔했으나, 이 중 76,091개(99%)가 버려지고 976개 행만 최종 결과로 사용되었다.

STEP 03

개선 조치

네 곳을 개선했다. 각 조치 항목에 연관된 병목 원인을 명시했다. 병목 ①(초당 4.4건 상한)은 개별 원인들의 합산 결과이므로 직접적인 수정 대상이 아니다. 아래 네 가지 조치가 병목 ①에 대한 해법이며, 최종 결과는 STEP 04에 정리했다. 모든 의사결정은 대안별 성능을 비교 측정한 뒤 선택했다.

01정렬을 이름순 → id순으로병목 ②

Primary Key(id) 기준 정렬을 적용하면 기본키 인덱스를 순차적으로 스캔하다가 필요한 20건을 충족하는 즉시 쿼리를 조기 종료(Early Stop)할 수 있다. 세 가지 정렬 후보를 비교 측정한 후 최적안을 선택했다.

정렬흔한 검색어희귀 검색어순서 안정성
이름순 (기존)182.6ms0.17msO
정렬 없음0.31ms0.07msX
id순 (채택)3.8ms0.08msO

정렬을 완전히 제거하면 속도는 가장 빠르지만, 동일한 검색어 요청에도 매번 다른 20건이 반환될 수 있다. DB가 조건에 매칭되는 10,135건 중 임의의 20건을 추출하여 반환하기 때문이다. 실제 '김밥' 검색 시 정렬 유무에 따라 반환되는 데이터 목록 자체가 완전히 달라짐을 확인했다.

id순 정렬은 이러한 결과의 재현성(안정성)을 보장하면서, 기존 이름순 정렬 대비 48배의 성능 향상을 확보했다.

02무한 스크롤을 포기하고 개수 세기를 없앤다병목 ②

페이징 로직 구현이 완료된 상태였으나, UX와 성능 간의 트레이드오프를 고려해 무한 스크롤 기능을 제외하고 20건 단건 노출 방식으로 전환했다. 검색 화면의 본질은 특정 대상을 찾는 것이지 전체 목록을 탐색하는 것이 아니므로, 상위 20건 내에 결과가 없으면 스크롤을 내리기보다 검색어를 재입력하는 것이 더 효율적인 사용자 행동 패턴이라고 판단했다.

페이징 로직을 제거함에 따라 불필요해진 전체 개수 조회(COUNT(*)) 쿼리도 함께 제거했다. 이에 따라 단일 검색 요청 시 실행되던 DB 쿼리 수 역시 2개에서 1개로 단축되었다.

03DB가 실제 검색어를 보고 실행 계획을 세우도록 변경병목 ③

01을 적용하고 재보니 회귀가 났다

흔한 검색어는 빨라졌는데 희귀한 검색어가 오히려 느려졌다. 조기 종료(Early Stop) 특성상 20건을 채울 때까지 인덱스를 계속 찾아야 한다. 그래서 검색 결과가 적을수록 20건을 채우기 위해 더 멀리까지 훑게 되면서 시간이 오래 걸린 것이었다. 

결과 20,964건 → 2ms      결과 47건 →  70ms
결과 10,135건 → 2ms      결과 21건 → 227ms

원인DB의 실행 계획 고정(Generic Plan)

DB(PostgreSQL)는 같은 쿼리가 5번 이상 실행되면 검색어 파라미터와 상관없이 고정된 실행 계획을 재사용한다. 이로 인해 검색어마다 다른 결과 건수를 예측하지 못했다.

해결Custom Plan 강제 적용

DB 접속 옵션에 force_custom_plan을 추가해, 매번 입력된 검색어에 맞춰 최적의 실행 계획을 세우도록 했다. 

?options=-c plan_cache_mode=force_custom_plan
결과 건수20,96410,1351,112472117
적용 전2ms2ms6ms70ms227ms217ms
적용 후6ms8ms12ms6ms3ms4ms

설정 적용 후 느렸던 희귀 검색어(227ms → 3ms)를 포함해 전 구간에서 3~12ms 수준의 균일한 성능을 확보했다.

매번 계획을 짜면 그 비용은 얼마인가

"매 요청마다 실행 계획을 다시 수립하면 CPU 오버헤드가 크지 않은가"라는 정당한 의문이 생길 수 있다.
이에 계획 수립 시간(Planning Time)과 실제 실행 시간(Execution Time)을 분리해 검증했다. 

계획을 새로 짜는 비용     0.03 ~ 0.08ms
계획을 잘못 골랐을 때        133ms   ← 1,600배

대안 검증: 실행 계획을 하나로 고정하는 경우
쿼리 구조를 변경해 특정 인덱스 경로로 고정하는 방법도 시도했다. 인덱스를 강제하면 희귀 검색어는 0.06ms로 개선되었으나, 반대로 흔한 검색어가 0.4ms에서 479ms로 급증했다. 검색어 분포(흔함/희귀)에 따라 최적의 접근 방식이 달라지므로, 어느 한쪽으로 고정하는 방식은 성립하지 않았다. 결국 매번 최적의 계획을 선택하는 것이 유일한 해법이었다.

이 설정은 접속 전체에 걸려서 검색이 아닌 쿼리도 매번 계획한다. 평범한 조인 쿼리로 재보니 계획 시간이 0.065ms로, 초당 150건을 받아도 코어 하나의 3% 수준이었다.

04필요한 만큼만 넓혀서 찾기병목 ④

앞의 4개의 개선점을 고치고 나니 이번엔 위치 기반 검색이 가장 느린 경로가 됐다(22.6ms). 그래서 1km 반경부터 시작해 결과가 부족할 때만 범위를 점진적으로 넓히는 방식으로 변경했다.

왜 답이 달라지지 않나

어차피 가까운 순으로 정렬해서 앞의 20개만 보여준다. 1km 안에 이미 20개가 있으면 그보다 먼 가게는 그 20개 안에 못 든다. 따라서 탐색 범위를 줄여도 기존 10km 검색과 완전 동일한 결과를 보장한다.

가까운 곳에 없으면 끝까지 넓힌다. 3.7km·7.2km 떨어진 가게도 그대로 찾아내며, 그 동작을 테스트로 검증 했다.

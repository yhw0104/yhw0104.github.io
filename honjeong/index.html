Part 1  핵심 기능과 기술적 도전 과제Key Accomplishments

A1  식당 데이터를 외부 API가 아니라 우리 DB의 마스터로

카카오 로컬 API로 붙일 계획이었으나, 개발 전 약관 확인에서 검색 결과를 영구 저장할 수 없다는 것을 알았습니다. 식당마다 체크인·리뷰·즐겨찾기가 쌓이는 구조라 장소가 우리 DB에 없으면 도메인이 성립하지 않습니다.

매 요청마다 외부 API를 부르면 검색 응답이 그쪽 지연·쿼터에 묶이고 장애까지 함께 받습니다. 그래서 공공데이터 전국일반음식점 65만 건을 우리 DB의 마스터로 적재하고, 카카오는 지도 렌더링 전용으로 앱이 직접 로드하게 분리했습니다.

결과적으로 검색에서 외부 API 호출이 0회가 되어, 응답이 우리 DB 성능에만 의존하게 됐습니다 — Part 2의 병목이 순수하게 우리 쿼리 문제인 이유입니다.

A2  규칙을 코드가 아니라 스키마에 둔다

체크인 상태는 다섯 개입니다(SEEKING 모집중(시작 지점) / ACTIVE 혼밥 중 / TOGETHER 같이 먹는 중 / ENDED 종료 / CANCELED 취소됨). 종료를 ENDED와 CANCELED 둘로 나눈 건 통계 때문입니다.

이 서비스의 존재 이유가 “혼자 혼밥하는게 나뿐만이 아니다”를 숫자로 보여주는 것이라, 체크인만 하고 5분 만에 나간 사람을 ‘오늘 혼밥한 사람들의 통계’에 넣으면 화면의 숫자가 거짓이 됩니다.

따라서 “진행 중 체크인은 최대 1개”라는 계획을 세웠습니다. 해당 문제를 서비스 계층에서 검사할 수도 있지만, 검사와 저장 사이에 다른 요청이 끼면 뚫리게 되어 해당 문제를 소스에서 판단하는것이 아닌 부분 유니크 인덱스로 DB에서 판단하도록 진행했습니다.

CREATE UNIQUE INDEX uq_check_ins_current_user
ON check_ins(user_id) WHERE status IN ('SEEKING','ACTIVE','TOGETHER');

이 인덱스 하나가 동시성 문제까지 같이 막아 줍니다.

버튼을 빠르게 두 번 누르면 요청 두 개가 거의 동시에 들어옵니다. 서비스 코드에서 “이미 진행 중인 체크인이 있나?”를 검사해도, 두 요청이 나란히 ‘없다’로 판단하여 체크인이 두개가 INSERT 될 수 있습니다.
하지만, 해당 문제를 DB에서 막는다면 첫 INSERT는 통과가 되지만, 두번째 INSERT는 통과되지 못합니다. 이 위반 예외를 잡아 409로 바꿔 “이미 진행 중인 체크인이 있습니다”로 보여줍니다. 검사를 코드에만 두면 이렇게 새지만, 스키마에 두면 어떤 경로로 들어와도 똑같이 지켜집니다.

배운 것 — 모든 검증을 DB로 내릴 수는 없지만, 깨지면 서비스의 의미가 무너지는 규칙은 스키마에 두는 편이 안전합니다. 여기서는 ‘진행 중 체크인 1개’가 통계의 신뢰도와 직결돼 그 기준이 됐습니다.

Part 2  성능 개선과 트러블슈팅Troubleshooting

B1  검색이 초당 4.4건에서 포화한다

상황
k6로 부하를 걸어 보니 장소 검색이 초당 4.4건에서 더 올라가지 않았고, 그때 DB CPU가 197%로 꽉 찼습니다. A1에서 외부 API를 걷어냈기 때문에 이 병목은 우리 쿼리 문제였습니다.
과제
운영은 소셜 로그인만 지원해서 테스트 사용자를 만들 수 없었습니다. 그래서 로컬에 운영 서버와 비슷한 조건을 세웠습니다. 로컬 컴퓨터가 운영 서버보다 더 빠르니 절대값을 쓰지 못해
개선 전/후 비율로만 판단했습니다.
행동
① ORDER BY name이 20건만 필요한 검색에 65만 행을 전부 정렬하게 만들었고,
② Page로 반환하면 자동으로 붙는 COUNT 쿼리가 상당한 부하를 차지하고 있었습니다.
정렬 키를 기본키로 바꾸고 페이징을 걷어냈습니다. 그런데 이 수정이 새 문제를 만들었습니다.드물게 쓰이는 검색어에서 응답이 227ms로 오히려 느려졌는데, PostgreSQL이 한 번 세운 실행 계획을 계속 재사용하면서 인덱스를 타지 않은 탓이었습니다. 매번 계획을 새로 세우도록 설정(plan_cache_mode)을 바꿔 3ms로 잡았습니다.
결과
지표개선 전개선 후변화
처리량 (장소 검색)4.4건/초150건/초 이상34배 이상

배운 것 — 고쳤다는 사실보다 내 수정이 만든 문제를 스스로 찾은 것이 중요했습니다. 그건 고친 뒤에 다시 재봐야만 보입니다. 같은 측정에서 채팅 목록의 N+1도 발견했지만 대화방당 0.03ms라 고치지 않기로 했습니다.

B2  매칭이 깨지면 남겨진 사람이 갇힌다

상황
매칭이 성사되면 두 사람 각각에게 TOGETHER 체크인이 생깁니다. 둘 중 한 명이 자리를 뜨는 기능을 처음엔 “떠나는 사람의 체크인만 TOGETHER에서 빼면 된다”고 만들었습니다.
그랬더니 남겨진 사람은 TOGETHER 상태에 그대로 있었습니다. 알림도 가지 않아 앱에는 “○○님과 같이 먹는 중”이 계속 떠 있었습니다.
과제
이에 따라, 매칭 취소한 사람의 행동이 남겨진 사람을 같이 먹는 상태에 묶어두면 안된다라는 것을 확인했습니다. 매칭을 깨는 일을 ‘내 상태만 바꾸기’가 아니라 두 사람의 체크인과 대화방을 함께 정리하는 한 트랜잭션으로 다시 정의했습니다.
행동
남겨지는 쪽은 항상 SEEKING(모집중)으로 되돌립니다. 만들면서 순서 문제가 나왔습니다. 두 체크인을 이어 주는 값이 mealRequestId인데 leaveMatch() 안에서 null이 되기 때문에, 떠나는 사람의 체크인을 먼저 바꾸면 남겨진 사람도 대화방도 찾을 수 없습니다.
// mine: 매칭 취소를 요청한 사람의 체크인 / partner: 남겨진 사람의 체크인
Long mrId = mine.getMealRequestId(); // ① 지워지기 전에 캡처
checkInRepository.findTogetherByMealRequestId(mrId) // ② 짝을 찾아
.stream().filter(x -> !x.isOwnedBy(userId)).findFirst()
.ifPresent(partner -> partner.leaveMatch(SEEKING, now)); // ③ 모집중으로
mine.leaveMatch(to, now); // ④ 여기서 mealRequestId가 null
conversationService.close(mrId); // ⑤ 대화방도 함께 닫는다
그리고 “매칭이 풀리면 대화방도 닫는다”를 규칙으로 정해, 매칭이 풀릴 수 있는 5곳(체크인 종료 · 매칭 나가기 · 시간 만료 · 차단 · 탈퇴)을 전부 같게 맞췄습니다.
결과
남겨진 사람이 모르는 채 묶여 있는 경우가 없어졌고, 관계가 끝난 뒤에도 메시지를 보낼 수 있던 구멍이 5곳 모두 닫혔습니다.
배운 것 — TOGETHER는 혼자 성립할 수 없는 상태라, 한쪽만 풀면 데이터가 앞뒤가 맞지 않게 됩니다. 이후로는 같이 바뀌어야 하는 것을 한 트랜잭션으로 묶습니다.

B3  로그아웃이 실패하면 되돌릴 방법이 없었다

상황
로그아웃은 ① 서버 DB에서 푸시 토큰을 지우고 ② FCM에서도 폐기하는 두 단계입니다. 정상이면 즉시 사라집니다. 그런데 둘 다 실패하면 DB에는 행이 남았는데 기기에는 토큰 값이 없습니다. 이 행을 지우려면 토큰 값으로 찾아야 하는데 그 값을 아는 곳이 어디에도 없어, 아무도 지울 수 없는 행이 됩니다.
ex) 그 폰을 중고로 산 사람의 잠금화면에 이전 주인의 알림이 계속 뜹니다. 기능 문제가 아니라 개인정보 사고입니다.
과제
문제는 복구 경로가 하나도 없다는 것이었습니다. 네트워크 실패는 반드시 일어나므로 재시도로 없앨 수 없습니다. 그래서 실패를 전제로, 앱이 부탁하지 않아도 서버가 스스로 정리하는 회수 경로를 세 겹으로 깔았습니다.
행동
어느 하나에 실패해도 다음 겹이 받아 냅니다.
재등록 시
V27		같은 기기에서 새 토큰(새 로그인)이 등록되면 그 기기의 옛 토큰을 지웁니다. 토큰은 값이 바뀌어 옛 행을 찾을 수 없지만, 설치 ID(installation_id)는 앱을 지울 때까지 그대로라 찾아낼 수 있습니다.
발송 시FCM이 영구 무효(UNREGISTERED)로 판정한 토큰은 발송 직후 그 행을 지웁니다. 앱이 삭제된 기기가 여기서 걸립니다.
60일 후
V26		둘 다 안 걸린 행의 최후 안전망입니다. 앱이 등록할 때만 찍히는 컬럼(last_registered_at)을 따로 만들어 기준으로 삼았습니다.
결과
아무도 지울 수 없던 행이 세 겹 중 하나에는 반드시 걸리게 됐고, 대부분은 다음 로그인 순간 정리됩니다.
배운 것 — 성공하는 경우만 생각할 게 아니라, 실패했을 때 어떻게 되는지도 같이 정해야 합니다. 실패 자체는 막을 수 없어도 되돌릴 방법은 미리 만들어 둘 수 있습니다.

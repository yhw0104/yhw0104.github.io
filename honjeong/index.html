장소 검색이 초당 4.4건에서 멈춘다 — 처리량 34배 개선 부하 테스트

문제
k6 부하 테스트에서 장소 검색이 초당 4.4건에서 더 오르지 않고 DB CPU가 197%로 포화됐습니다. 공공데이터 식당 65만 건을 자체 DB에 적재하여 외부 API 호출은 따로 없었습니다. 따라서 병목은 우리 쿼리에서 나오는 문제였습니다.
원인
DB 로그로 검색 1건(722ms)을 나눠 보니 ① 이름순 정렬(424ms) — 20건만 필요해도 조건에 맞는 행을 전부 찾아 정렬했고, ② 페이징(Page)이 자동으로 붙이는 COUNT 쿼리(298ms) — 화면에서 쓰지 않는 총 건수를 매번 셌습니다.
해결
정렬 기준을 기본키로 바꿔 인덱스 순서대로 20건만 가져오도록 하고, 페이징과 COUNT를 제거하여 부하를 줄였습니다. 재측정하니 이번엔 결과가 적은 검색어만 227ms로 느려졌습니다. 확인해보니, PostgreSQL은 같은 쿼리를 5번 실행하면 검색어 값을 보지 않고 실행 계획을 고정하는 문제가 있었습니다. 따라서 매번 실제 검색어로 계획을 세우도록 설정(plan_cache_mode)을 바꿨습니다.
검증

버튼을 두 번 누르면 체크인이 두 개 생긴다 — DB 부분 유니크 인덱스

문제
이 서비스는 ‘지금 혼밥 중인 사람 수’를 보여주는 것이 핵심이라, 한 사람의 진행 중 체크인은 1개여야 숫자가 맞습니다. 그런데 버튼을 빠르게 두 번 누르면 체크인이 두 개 생길 수 있는 문제가 발생 했었습니다.
원인
서비스 코드에서 “진행 중 체크인이 있나?”를 검사한 뒤 저장하면, 거의 동시에 들어온 두 요청이 각각의 트랜젝션으로 판단해 둘 다 ‘없다’로 체크하고 각각 INSERT합니다.
해결
규칙을 코드가 아니라 DB 부분 유니크 인덱스로 강제했습니다. 두 번째 INSERT는 DB가 거절하고, 이 예외를 409 “이미 진행 중인 체크인이 있습니다”로 바꿔 응답합니다.
CREATE UNIQUE INDEX uq_check_ins_current_user ON check_ins(user_id)
WHERE status IN ('SEEKING','ACTIVE','TOGETHER');
결과
요청이 동시에 들어와도 진행 중 체크인은 항상 1개만 남아, 중복 체크인으로 숫자가 틀어지던 동시성 문제를 해결했습니다.

매칭을 나가면 남겨진 사람이 갇힌다 — 트랜잭션

문제
매칭된 두 사람 중 한 명이 체크아웃 해도 남겨진 사람은 “같이 먹는 중” 상태에 그대로 남았고, 알림도 가지 않았습니다.
원인
매칭 체크아웃을 ‘나가는 사람의 상태만 바꾸도록’ 초기에 개발 했었습니다. 게다가 두 체크인을 잇는 mealRequestId가 상태 변경 중에 null이 되어, 내 상태를 먼저 바꾸면 상대와 대화방을 찾을 수 없었습니다.
해결
매칭 해제를 두 사람의 체크인과 대화방을 함께 정리하는 한 트랜잭션으로 다시 정의했습니다. 연결 값을 먼저 꺼내 두고, 남겨진 사람은 모집중으로 되돌린 뒤 대화방을 닫습니다.
Long mrId = mine.getMealRequestId(); // ① 지워지기 전에 꺼내 둔다
partner.leaveMatch(SEEKING, now); // ② 남겨진 사람은 모집중으로
mine.leaveMatch(to, now); // ③ 여기서 mealRequestId가 null
conversationService.close(mrId); // ④ 대화방도 함께 닫는다
결과
매칭이 풀리는 5곳(체크인 종료 · 매칭 나가기 · 시간 만료 · 차단 · 탈퇴)을 같은 규칙으로 맞춰, 남겨진 사람이 묶여 있거나 관계가 끝난 뒤 메시지를 보낼 수 있던 구멍을 모두 닫았습니다.

탈퇴를 했지만 탈퇴가 안 된다 — 영속성 컨텍스트

문제
회원 탈퇴 후 개인 데이터는 지워지는데 계정 상태는 그대로 ACTIVE였습니다(휴대폰 번호, 닉네임이 남아 재가입도 막힘).
원인
정리 작업에서 일괄 삭제 쿼리 11곳에 넣은 @Modifying(clearAutomatically = true)가 영속성 컨텍스트 전체를 비워, 먼저 조회해 둔 회원 객체가 일괄 삭제 후, 관리 대상에서 빠졌습니다. 그 뒤의 탈퇴 처리는 객체가 없어 UPDATE가 되지 않았습니다.
해결
11곳의 옵션을 되돌리고, 각 메서드에 재발 방지 주석을 남겼습니다.
결과
탈퇴 시 계정 상태가 정상적으로 바뀌고, 실제 DB로 돌리는 회귀 테스트를 추가해 같은 문제가 다시 생기면 배포 전에 바로 실패하도록 막았습니다.
